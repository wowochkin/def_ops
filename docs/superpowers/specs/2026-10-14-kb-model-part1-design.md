# База знаний ↔ моделирование, часть 1: типизированные факты, сборщик «база → модель», изменения по датам в движках

## Цель

База знаний — не справочник сбоку, а основа модели. Документы пополняют базу, база питает модель, у каждого входа
модели видно, на чём он держится. Часть 1 строит основу:

1. факты базы получают формальную часть (вид, о ком, когда, значение);
2. сборщик «база → модель» превращает факты в поправки к операции;
3. оба движка исполняют изменения по датам (пополнения, переподчинение), сверяют численность с документальной,
   а принятие командования начинается с состояния по самым надёжным фактам;
4. в «Моделировании» — вкладка «Основа модели»: на чём держится каждое число, расхождения, доля допущений.

Это часть 1 из 4 (подход «типизированные факты и сборщик поверх нынешних данных»). Дальше: 2 — документы → факты
всех видов и правка фактов; 3 — правила из базы (нормативы со значениями, калибровка в их границах); 4 — советник,
посредник и штаб противника на той же базе.

## Решения, принятые с заказчиком

| Вопрос | Решение |
|---|---|
| Подход | Типизированные факты и сборщик поверх нынешних данных; встроенные данные остаются основой, база даёт поправки и показывает источники |
| Несколько фактов об одном | Автоматически: надёжность (A > B > C) → близость даты к нужному моменту → более свежий документ. Расхождения видны списком; выбор можно закрепить вручную |
| Изменения по ходу операции | Сразу учим движок: пополнения и переподчинение по датам |
| Какой движок | Оба (нынешняя модель и агентная), по одной общей схеме изменений |
| Документальная численность | Переигровка и калибровка — контрольная точка для сверки (не подставляется); принятие командования — состояние ставится по фактам на дату передачи |

## 1. Типизированный факт

`packages/knowledge/src/schema.ts`, `Fact` — добавляется необязательное поле `claim` (формальная часть). Текстовые
поля (`key`, `value`, `source`, `pages`, `reliability`, `quote`) остаются; факт без `claim` — как сейчас, только
справка.

```ts
type Claim =
  | { kind: 'strength'; subject: string; at: string; personnel?: number; tanks?: number; guns?: number }
  | { kind: 'reinforce'; subject: string; at: string; personnel?: number; tanks?: number; guns?: number }
  | { kind: 'parent'; subject: string; from: string; parent: string }
  | { kind: 'enter'; subject: string; at: string }
  | { kind: 'position'; subject: string; at: string; place?: string; lngLat?: [number, number]; uncertaintyKm?: number }
  | { kind: 'boundary'; between: [string, string]; from: string; to?: string; points: string[]; inclusive?: string }
  | { kind: 'crossing'; subject: string; from: string; state: 'open' | 'destroyed' | 'built' }
  | { kind: 'event'; id: string; at: string; title: string; place?: string }
  | { kind: 'losses'; subject: string; from: string; to: string; killed?: number; wounded?: number; missing?: number; tanks?: number };
```

- `subject` — id формирования сценария (`su_61a`, `de_9fjd`) или объекта театра (мост); сопоставление названия с id —
  тем же кодом, что сверка (`packages/knowledge/src/sync.ts`).
- Даты — ISO (день или момент). `strength` — состояние на дату; `reinforce` — прибавка на дату; `parent` действует
  с `from`.
- Надёжность и источник — у факта (`reliability`, `source`), не в `claim`.

### Выбор из нескольких

Чистая функция `resolve(facts, kind, subject, moment, pins)` (`packages/knowledge/src/resolve.ts`):

1. кандидаты — факты с `claim` того же вида и `subject`, действующие на момент (`at ≤ moment` для состояния и
   подчинённости; для начального состояния — ближайшие к началу операции в пределах ±2 суток, как сейчас в сверке);
2. закрепление (`pins[key]`, где `key = kind|subject|moment`) — берётся закреплённый факт;
3. иначе — наибольшая надёжность (A > B > C; без надёжности — C), затем меньшее |дата − момент|, затем более свежий
   документ (`updatedAt` записи или дата документа);
4. расхождение — если у кандидатов разные значения (численность — разница больше 5 % и порога сверки
   `reconcile`); в выход идёт список расхождений.

Закрепления хранятся в слое пользователя базы (IndexedDB `def_ops_kb`, новое хранилище `pins`), входят в выгрузку
и загрузку материалов.

### Сид встроенных операций

`packages/knowledge/tools/build_seed.ts` выпускает `claim` из тех же `docs/sources`, из которых собран сценарий:

| Источник | Вид |
|---|---|
| состав и численность (`berlin-1945-divisions.json`, `-german-forces.json`, `-seelow-divisions.json`, дивизионный состав агентного сценария) | `strength` на начало, `parent`, `enter` |
| положения (`berlin-1945-positions.json`, выписки ЦАМО) | `position` |
| разграничительные линии (`*-boundaries.json`) | `boundary` |
| объекты (`berlin-1945-objects.json`: мосты, переправы) | `crossing` |
| ежедневные потери (`berlin-1945-losses-daily*.json`) | `losses` за период (убито, ранено, пропало) — контрольные точки накопленных потерь |

Остатки дивизий (`division-remnants-1945.json`) — общие правила и текстовые примеры без чисел по дивизиям;
формальных частей в части 1 не дают.
| события истории сценария | `event` |

Допущения сборщика сценария (медиана известных дивизий и т. п.) фактами не становятся — во «Основе модели» они
видны как допущения.

## 2. Сборщик «база → модель»

Чистая функция `compileOperation(kb, op, pins) → { edits, provenance, conflicts }`
(`packages/knowledge/src/compile.ts`), где `op` — сценарий операции (уровень армий) и агентный сценарий
(уровень дивизий), если есть.

Выход `edits` — расширение `OperationEdits` (`apps/editor/src/sim/userdata.ts`):

- `formations` — начальные численность, подчинённость (`parent`), `enterAt` (сейчас — только численность);
- `changes` (новое) — изменения по датам: `{ at, formation, kind: 'reinforce' | 'resubordinate', personnel?, tanks?, guns?, parent?, fact }`;
- `checkpoints` (новое, в историю) — численность на дату `{ at, formation, personnel?, tanks?, guns?, fact }` и
  накопленные с начала операции потери `{ at, formation, losses, fact }` (сумма `losses` по `to ≤ at`);
- `positions`, `boundaries` — как сейчас; события — в `history.events`;
- переправы — в нынешние правки инфраструктуры (`saveInfra`).

`provenance` — для каждого входа (формирование × поле, изменение, контрольная точка, линия, переправа) ссылка на
выбранный факт (запись, факт, источник, надёжность, цитата) или пометка «допущение сценария». `conflicts` — список
расхождений с кандидатами.

Сейчас поправки пишутся вручную («принять»); после части 1 они пересобираются сборщиком при изменении базы.
Ручные действия нынешней сверки становятся закреплениями. Отклонённое (`dismissed`) — закрепление «не брать».

**Воспроизводимость.** Тест: сборщик на одной встроенной базе (сид) даёт для Берлинской операции начальное
состояние, совпадающее со встроенным сценарием (численность, подчинённость, `enterAt` по всем формированиям,
где у сценария есть источник). Расхождение — ошибка в формальных частях сида.

**Журнал изменений.** При изменении базы сборщик пересобирает поправки; если выход для операции изменился —
запись в журнал операции (`logChange`, вид `kb`) с перечнем изменённых входов. Панель пересчёта видит это как
«данные изменились».

## 3. Движки

### Нынешняя модель (`packages/sim`)

- `Scenario` (`types.ts`): поле `changes?: ScenarioChange[]`; поправки накладываются при чтении (`getData`).
- `step.ts`: в начале шага, рядом с вводом по `enterAt` и выделением `detachFrom`, исполняются наступившие
  изменения: `reinforce` прибавляет к численности, танкам, орудиям (и к исходным, по которым считается доля сил),
  `resubordinate` меняет `parent`. События журнала: `reinforced`, `resubordinated`.
- `History` (`history.ts`): `checkpoints?: StrengthCheckpoint[]`.
- Сверка: `compareStrength(run, history)` — доля контрольных точек в пределах ±25 % документа (численность — против
  расчётной; потери — против расчётных накопленных: начальные + пополнения − текущие), медиана расхождения, по
  формированиям и дням. В отчёте переигровки (`report.ts`) — свой раздел.
- Калибровка (`calibrate.ts`, `evaluateRules`): если контрольных точек в обучающей половине не меньше 10, мерило =
  ¾ нынешнего + ¼ доли численности в допуске; иначе — как сейчас.

### Агентная модель (`crates/agents-core`)

- Команды `run_scenario` и `game_start` (`crates/agents-tauri/src/lib.rs`, `agents-game.rs`) принимают
  `edits: { divisions?: {id: {personnel?, tanks?, guns?, hq?, enter?}}, changes?: [...] }` — как сейчас `params`.
- `scenario.rs` (`load_with`): начальные значения дивизий и подчинённость — из `edits`; изменения — в список
  событий модели; исполняются в часовом шаге.
- Оценка (`packages/sim/src/agents-score.ts`): контрольные точки — третья составляющая (доля в ±25 %), с тем же
  правилом веса, что у нынешней модели.

### Принятие командования (оба движка)

- Прогон по сценарию до момента передачи — как сейчас.
- Затем состояние соединений на дату передачи — по `resolve` на этот момент: численность (`strength` не старше
  суток), подчинённость (`parent`), положение (`position` не старше суток, неопределённость не больше допуска
  ступени: армия 15 км, корпус 8, дивизия 5).
  - Нынешняя модель: `startGame` (`packages/sim/src/game.ts`) после прогона.
  - Агентная: `Game::start_free` (`crates/agents-core/src/game.rs`) после прогона до `takeover` — по полю
    `takeoverState` в `game_start`.
- Окно принятия командования — сводка: «по фактам поправлено N соединений (численность X, положение Y,
  подчинённость Z); на допущениях — M», ссылка на «Основу модели».

## 4. Интерфейс

### «Моделирование» → операция → вкладка «Основа модели»

- **Формирования** (дерево по подчинённости): начальные численность, танки, орудия, подчинённость, ввод; ниже —
  изменения по датам и контрольные точки. У каждого числа — значок надёжности (A/B/C/допущение); по щелчку —
  источник, страницы, цитата, запись базы.
- **Расхождения**: выбранный по правилу факт и остальные кандидаты с надёжностью и датой; «закрепить этот» /
  «снять закрепление».
- **Итог**: доля входов модели на A / B / C / допущениях — по видам (численность, подчинённость, положения,
  линии, переправы).

### Запись базы

Факты с `claim` — таблицей (вид, дата, значение, источник, надёжность) с пометкой «в модели» / «перебит фактом …» /
«не используется» (для операций, к которым относится запись).

## Проверка

- Юнит-тесты: `resolve` (надёжность, дата, свежесть, закрепления, расхождения); `compileOperation` (все виды,
  провенанс); воспроизводимость Берлинской операции из сида; исполнение `reinforce` / `resubordinate` в
  `step.ts`; `compareStrength`; мерило калибровки с контрольными точками; ядро — тесты Rust на изменения и
  `takeoverState`; состояние при принятии командования (обе модели).
- Переигровка Берлинской операции до и после (нынешняя и агентная модели); цифры в описание — только из свежего
  прогона.
- Снимки: вкладка «Основа модели» (формирования, расхождения, итог), окно принятия командования со сводкой.
- По правилам репозитория: описание `docs/system.md` (части I и II), `npm run kb:seed`, `docs:system`,
  `typecheck`, `test`.

- Нормативы со значениями и правила из базы — часть 3.
- Посредник и штаб противника на пользовательской базе — часть 4.
