# База знаний ↔ моделирование, часть 4: советник, посредник, штабы и Ставка на одной базе

## Цель

Сейчас языковые модели игры получают знания по-разному: советник — справку из всей базы (встроенная + слой
пользователя, отбор по операции, смысловой поиск), посредник — только встроенный сид по словам, штаб противника и
Ставка — ничего, штабы агентной модели — доктрину, зашитую в код. Часть 4 сводит всё к одной базе:

1. **Одна справка** для всех ролей — встроенная база, слой пользователя, закрепления, отбор по операции, смысловой
   поиск — с правилом «что может знать роль» (сторона, история, момент).
2. **Доктрина — формальные факты базы**: правила «условие → действие» с числами, источником и надёжностью;
   извлекаются из документов и правятся вручную, как прочие факты.
3. **Штабы на доктрине из базы**: штаб противника и Ставка получают правила своей стороны, подходящие к обстановке;
   штабы агентной модели — текст доктрины, собранный из базы, вместо зашитого.
4. **Видно, на чём решение**: у решений штаба, поправок посредника и ответов советника — ссылки на записи базы.

Это часть 4 из 4.

## Решения (приняты исполнителем без заказчика, по образцу частей 1–3)

| Вопрос | Решение | Почему |
|---|---|---|
| Где строится справка | В окне (там база с векторами и закреплениями); поток игры просит справку сообщением, ответ — с ограничением по времени; без ответа — прежний поиск по сиду | один путь вместо двух; поток не держит свою копию базы |
| Что знает штаб противника | доктрина своей и чужой стороны, организация, техника, местность операции; без истории операции, положений и потерь из документов | туман войны: штаб не знает будущего и чужих донесений |
| Что знает посредник | доктрина, нормативы, техника, местность; без хода операции | поправки — по правилам и опыту, не подгонка под историю |
| Что знает советник | как сейчас (история — только в теме «история») + слой пользователя | без изменений по смыслу |
| Что знает Ставка | доктрина советской стороны (уровень фронта/армии), директивы — как сейчас | разграничения решаются по правилам, не по будущему |
| Вид факта доктрины | новый вид `doctrine` (сторона, уровень, группа, условие, действие, числа) | число правил ~140, нужны отбор по группе и числа для ядра |
| Отбор доктрины к обстановке | по триггерам обстановки → группы (прорыв — контрудар/резервы; давление — отход; окружение — прорыв; наступление — эшелоны/ввод/темп) + поиск по тексту; не больше 8 правил, 4000 знаков | короткий и уместный блок вместо всей доктрины |
| Штабы агентной модели | текст доктрины передаётся из окна в ядро при запуске расчёта (необязательное поле); числа доктрины ядра остаются из `agents-v0.json` | текст — то, что видит модель; числа ядра настраиваются калибровкой части 3 |
| Ссылки в решениях | поле `basis: string[]` (`R1`…) в ответах штаба и Ставки, как у посредника; несуществующие ссылки отбрасываются | проверяемо и без лишних полей |

## 1. Справка по роли

`packages/knowledge/src/role-reference.ts`:

```ts
type Role = 'advisor' | 'umpire' | 'staff' | 'stavka' | 'review';
interface RoleScope { role: Role; side?: 'su' | 'de'; operation?: string; moment?: string; history?: boolean }
roleFilter(scope): (e: Entry) => boolean
roleReference(index, byId, queries: string[], scope, o: { limit; chars; hits? }): { refs: Ref[]; text: string }
```

- Политика ролей — таблица выше; общая основа — `gameReference` (без записей модели и источников, `foreignTo`).
- `staff`/`stavka`/`umpire`: без категорий хода операции (operations, battles, chronology), без записей-документов
  операции с положениями/потерями; доктрина — обеих сторон, помечается стороной.
- `review` (разбор после игры): всё, включая историю.
- Ссылки нумеруются `R1…`, у каждой — id записи; текст записи режется до `chars`.

Окно (`apps/editor/src/kb/kb.ts`): `roleRef(queries, scope)` — гибридный поиск (как `reference`). Поток игры
(`game-worker.ts`): сообщение `kbRef` → ответ `kbRefResult`; ожидание до 8 с, иначе — прежний поиск по сиду
(`umpireRefs`), в журнале — «справка без слоя пользователя». Оценка посредника в Node (`umpire-ab.ts`) — через
`roleReference` по сиду.

## 2. Доктрина в базе

```ts
| { kind: 'doctrine'; side: 'su' | 'de'; level: 'front' | 'army' | 'corps' | 'division'; group: string; rule: string;
    condition: string; action: string; values?: Record<string, number | [number, number]> }
```

- `rule` — id правила (`flank-attack-one-third`); ключ разрешения — `doctrine:<side>:<rule>` (без даты).
- Сид: `npm run kb:seed` превращает `docs/sources/german-defence-doctrine-1945.json`,
  `soviet-offensive-doctrine-1945.json` и `…-tsamo.json` в факты записей доктрины (`org:de-doctrine-<group>`,
  `org:su-doctrine-<group>`; нет записи — создаётся), прежние текстовые строки `principles` остаются.
- Документы (часть 2): вид `doctrine` в извлечении (только для кусков с признаками устава/наставления — как
  нормативы части 3), проверки: сторона и группа известны, условие и действие не пусты, число из `values` есть в
  цитате; форма факта — поля вида.
- Слова: «Доктрина (нем., корпус, контрудар): условие → действие; числа».

## 3. Штабы и Ставка на доктрине

- `doctrineFor(entries, pins, side, triggers, query) → { rules: DoctrineRule[]; text }` (`packages/knowledge`):
  разрешение по ключу (закрепление → надёжность → свежесть), отбор по группам триггеров и тексту, ≤ 8 правил.
- Триггеры обстановки (`services/staff/src/live/triggers.ts`): по `buildSituation` — вклинение противника в полосу,
  давление (соотношение ≥ 3 на участке), окружение своих, свой удар/наступление, резервы в тылу.
- Штаб противника (`situation.ts`, `staff.live.md`): новый слот `{doctrine}` — «Доктрина вашей стороны (из базы
  знаний)» и `{reference}` — справка роли `staff`. В ответе — `basis`.
- Ставка (`stavka.ts`): блок доктрины советской стороны уровня фронта/армии.
- Посредник: справка роли `umpire` вместо сида; запросы — прежние шаблоны + группы доктрины по бою.
- Штабы агентной модели: `run_scenario`/`game_turn` принимают `doctrine_text?: { su?: string; de?: string }`;
  `llm_hq`/`su_llm_hq` подставляют его вместо зашитого текста (числа в тексте — из фактов); без поля — как сейчас.
- Ограничения: доктрина ≤ 4000 знаков, справка ≤ 5 × 700; оценка токенов как в `decide.ts`.

## 4. Интерфейс

- «Посредник» в игре: у решения штаба противника — «по базе: R1, R3» со всплывающим заголовком записи; щелчок —
  запись в «Знаниях».
- Советник: ссылки ответа — как сейчас, но на записи слоя пользователя тоже.
- Запись базы: факты доктрины словами; форма факта — поля вида `doctrine`.
- «Знания» → запись доктрины: блок «Кто использует» — штаб противника / Ставка / посредник / штабы агентной модели.

## Проверка

Тесты: политика ролей (штаб не видит истории и документов операции, советник видит историю только в теме, разбор
— всё); поток игры получает справку от окна и без ответа — сид; сид доктрины (каждое правило — факт; id и числа
сохранены); `doctrineFor` — триггеры → группы, закрепление побеждает, ≤ 8 правил; промпт штаба с доктриной и
справкой; `basis` — несуществующие ссылки отброшены; ядро с `doctrine_text` подставляет его, без — прежний текст
(тест Rust); извлечение и проверки вида `doctrine` на записанных ответах. Описание (часть I — разделы 6, 8, 9;
часть II — «Что меняется при подключении ИИ»), снимки, `kb:seed`, `model:index`, `docs:system`; руководство
пользователя — абзац о том, что штабы и посредник опираются на базу.

## Вне части 4

Числа доктрины ядра агентной модели из базы (через коридоры части 3 — следующая итерация); голосовые/инструментальные
справки в разговоре с агентом.
